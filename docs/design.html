System Design · v0.1 draft · 2026-06-10

Agent Commander

Many AI coding agents report their status to a central commander; the commander pushes a live view to a small ESP32 device, and your voice — captured on that device, transcribed by the commander — flows back as a prompt to the right agent.

Lineage from agent-status. agent-status is one machine, read-only, zero-network: it tails the files Claude Code writes and shows them locally. Agent Commander inverts every one of those properties — many machines, bidirectional, networked — but reuses the hard-won insight: the cheapest way to know what an agent is doing is to read the state it already writes to disk. The SessionProvider protocol becomes the Agent Adapter; the local SessionStore becomes a cloud Commander; the Commander board becomes a physical device.

01System architecture

Three tiers, one bus, two directions

Adapters live on agent machines and speak the same interface regardless of agent type. The Commander is the only stateful, multi-tenant service. The device is a thin client: it renders templates it's handed and streams microphone audio. Each principal holds one authenticated WebSocket (WSS) connection to the Commander; bulk audio uses a second short-lived WS (see §11), and stateless operations go over REST.

02Components

What each tier owns

tier 1 · agent machine

Agent Adapter

One small process per agent type. Up: derives status from whatever the agent writes (Claude Code → tail the jsonl, reusing agent-status's parser). Down: injects a prompt via whatever the agent supports — tmux send-keys, native API, or SDK re-drive. Authenticates to the Commander as a specific agent within a tenant. Stateless beyond its own session map.

tier 2 · cloud

Commander

The only stateful, multi-tenant service (§03). Ingests status, holds the current snapshot per agent, fans out to the right devices, runs speech-to-text, routes transcribed prompts to the correct adapter, and owns auth / tenancy / device pairing. Decides what the device should render.

tier 3 · hardware

Beacon (ESP32)

Deliberately dumb. Holds one WS that receives "render this" messages and paints a fixed set of templates baked into firmware. Holds a push-to-talk button + mic; streams audio while held. Sends button/selection events back up. No business logic — the Commander drives the UX.

03Tenancy & identity

Multi-tenant at the core — there is no single-tenant mode

Tenancy is not a later milestone; it is the first invariant. Every user, device, and agent belongs to exactly one tenant, and isolation is enforced on every connection and every message from the first commit. The Commander never trusts a tenantId in a payload — it derives the tenant from the authenticated principal and stamps it on everything. A bug that lets one tenant see or command another is the highest-severity failure in the system.

isolation

Tenant-stamped, never trusted

Every WS upgrade and REST call resolves a principal → one tenantId. The Commander stamps it onto each inbound message and rejects any id outside that tenant. Durable state is row-level partitioned by tenant_id; every query is tenant-filtered.

authorization

Within a tenant, still scoped

A device may command an agent only if same tenant and device→agent ownership/ACL allows it. Roles gate dashboard actions (invite users, issue agent keys, revoke devices). Per-tenant quotas & rate limits (agents, devices, STT minutes).

scale

Horizontal from day one

Commander nodes are stateless; WS connections shard across them. Cross-node delivery (an adapter on node A → a device on node B) goes through Redis pub/sub keyed by tenant; Postgres holds tenant-partitioned durable state. Add nodes, not special cases.

04Data flows

Two loops, end to end

Status up — the agent-status idea, over the wire Command down — the novel, higher-risk path

▲ STATUS UP

1
Adapter

Agent writes a line to its transcript; adapter's tailer folds it into a status snapshot (tool, tokens, context%, waiting state).

2
Adapter → WS

Sends the snapshot up its status channel. Throttled by a uiEqual-style gate so nothing is sent unless something visible changed.

3
Commander

Updates per-agent state, decides which device(s) subscribe to this agent, picks the right template, and renders.

4
Device

Receives {template,data}, paints the screen. An agent that flips to waiting can wake the screen / pulse an LED.

▼ COMMAND DOWN

1
Device

User holds PTT, speaks. Device streams Opus audio frames to the audio gateway, tagged with the agent currently in focus.

2
Commander · STT

Transcribes. May classify intent: a fresh prompt, an answer to a pending approval, or an interrupt.

3
Commander · router

Authorizes (this device may command this agent?) and pushes the command down that agent's live WS connection.

4
Adapter

Injects the prompt into the running agent via its mechanism, then publishes an ack (delivered / rejected).

5
Device

Shows a confirm template ("sent → Refactor auth"), then the normal status loop reflects the agent acting on it.

05Transport — WebSocket on one API stack

Persistent WSS per principal · REST for stateless ops

The Commander is not a relay — it transforms every status message into a render decision and authorizes every command — so a pub/sub broker would add a hop without removing the need for the app server. Instead, each principal holds one authenticated WebSocket to the Commander, carrying typed messages both directions. Stateless operations (login, pairing, registration, history) go over REST on the same stack. Tenant isolation lives in app-layer authz — the authenticated principal is bound to one tenantId; no broker ACLs to configure. On (re)connect the server sends current state (replacing retained messages); a ping/pong heartbeat marks a principal offline (replacing last-will).

06Message schemas

The wire contract — versioned, small, agent-agnostic

Every message carries v (schema version) so firmware and adapters can evolve independently. The status schema is the networked heir of agent-status's SessionSnapshot + EnrichedSession, flattened and trimmed to what a small screen and a router actually need.

07Agent Adapter interface

The bidirectional heir to SessionProvider

agent-status's SessionProvider was one-way (start()/stop() + a stream out). The adapter adds the return path — send() — and a connection to the bus. The interface is deliberately tiny so a new agent is, once again, "one new file." Shown in language-neutral pseudocode; the adapter SDK language is open (Go/Rust for a portable single binary, or Swift to literally reuse agent-status's tailer for the Claude Code adapter).

08Open adapter standard · ACAP

One public contract, so anyone can add an agent

An adapter's only real job is to normalize one agent into the canonical status schema (§06) and accept canonical commands. ACAP — the Agent Commander Adapter Protocol — is the open, versioned contract that fixes the wire shape, the connection lifecycle, and the capability handshake, while leaving how you read status and inject prompts entirely to the adapter. Read state however the agent exposes it — file tail, log, API, SDK; ACAP standardizes only what crosses the wire.

Conformance levels — ship at L0, grow upward

handshake

Declare, don't assume

On register (REST) and the WS hello, the adapter advertises its level, capabilities (intents it accepts) and provides (status fields it populates). The Commander tailors device UI and routing to exactly that.

conformance harness

acap-verify

A mock Commander + recorded fixtures runs the handshake, validates every message against the schema, checks that claimed capabilities actually behave, and exercises reconnect + heartbeat. Pass → self-certify, without touching production.

registry & governance

One PR to add an agent

Adapters live in an open registry — each a folder with a manifest (id, level, maintainer). Passing acap-verify + a PR = listed. Everything is versioned by the message v; new fields are additive and optional.

09Agent deep dives

The same contract, four very different agents

Each adapter maps a native agent into ACAP. The spread below is the range the standard has to absorb — from a file-tailing agent with no input API (Claude Code) to API-native agents built to be driven (openclaw, hermes). The Commander reads the matrix from each adapter's handshake, never from hard-coded assumptions.

Claude Code

L3 · Richstock interactive CLI · no native input API
▲ Status — read from disk

Reuses agent-status's TranscriptTailer verbatim: tail ~/.claude/projects/<cwd>/<sessionId>.jsonl for rich state and ~/.claude/sessions/<pid>.json for coarse status. Derives tool + duration, tokens / cost (per-message model pricing), context% incl. [1m], permission mode, todos, and the waiting / approval banner.

▼ Inject — mixed, no native API

pty / tmux send-keys into the stock interactive process: type the prompt, send option keys to answer an approval, ESC to interrupt. Or the Claude Agent SDK headless, where the adapter owns the loop and feeds prompts directly — cleanest, but the agent then runs under the harness.

promptanswerinterruptmode

Quirks the mapper handles: aiTitle key (not title); sidechain messages billed but excluded from turns/context; TodoWrite replaces the list while TaskCreate/Update are incremental; gitBranch stamped per record; [1m] = 1M-token window.

Codex

L1–L2OpenAI Codex CLI · non-interactive drive available
▲ Status — read from log

Tail Codex's per-session rollout / log file (JSONL) under ~/.codex/, mapping its turn, tool and usage events to the canonical schema. Exact paths and keys are confirmed per installed Codex version — the mapping table is the bulk of this adapter's work, since Codex's schema differs from Claude's.

▼ Inject — CLI / MCP / pty

codex exec (and resume) for a non-interactive drive, Codex's MCP server interface, or pty send-keys into the interactive TUI. Which one decides whether answer/interrupt are clean or best-effort.

promptanswerinterruptmodetodos

Note: until the mapping is filled in, Codex can ship at L0 (status only) the same afternoon and grow to L1/L2 as injection is wired.

openclaw

L3 · RichAPI-native agent · designed to be driven
▲ Status — subscribe

The ideal case: no file-tailing. The adapter subscribes to openclaw's native event stream (WS/SSE) and forwards a thin mapping — events arrive already structured. Concrete endpoints are defined by the openclaw project.

▼ Inject — native API

Commands map straight onto openclaw's input/control API (HTTP or RPC). Because it was built API-first, the full intent set — prompt, answer, interrupt, mode — is available cleanly.

promptanswerinterruptmodecosttodos

Why it matters: openclaw shows ACAP at its best — when an agent cooperates, the adapter is a few hundred lines of mapping over a stream. It's the template for new agents to aim at.

hermes

L2 · Interactivedaemon-style agent · local control socket
▲ Status — socket / RPC

A long-running daemon the adapter queries or subscribes to over a control socket / local RPC. The adapter is a thin RPC client mapping hermes state to canonical fields; cost & todos are partial until hermes surfaces them.

▼ Inject — same socket

Prompts, approval answers and interrupts go back down the same control channel. Permission-mode switching is mechanism-dependent. Endpoint specifics are owned by the hermes project.

promptanswerinterruptmodecost

Pattern: hermes represents the daemon class — an always-on agent with a local control plane the adapter wraps.

Your agent here

L0 in an afternoon

Emit canonical status from whatever your agent already writes → that's L0, read-only, on the board immediately. Add send() for L1. Run acap-verify ./adapters/youragent, open a PR to the registry, and it ships. The hard parts — transport, auth, reconnect, fan-out, STT, the device — are already done. An adapter is a mapping, not a system.

10Device UI protocol

Server-driven UI — fixed templates, dynamic data

The Beacon is a circular ~6 cm display, so templates are designed circular-safe — content centred, the perimeter reserved as a gauge. The firmware ships a small, fixed set of templates; the Commander never sends layout, only {template, data}. This keeps firmware stable (no OTA to change a screen), keeps payloads tiny, and lets all UX logic live server-side. New screens are rare and deliberate. 11Audio path

Out-of-band from the control connection

Streaming audio over the device's control WS would head-of-line-block status and UI traffic behind big binary frames. Instead, push-to-talk uses a dedicated, short-lived second WS: the device announces intent on its control connection, then opens an audio WS straight to the Commander's audio gateway.

1
control WS

On PTT-down, device sends type:"audio.start" with the focused agentId. Commander replies with a one-time wss://api/audio token.

2
audio ws

Device streams Opus frames (≈16 kHz mono, ~12–24 kbps) over WebSocket/TLS while the button is held. ESP32 can encode Opus; raw PCM is the fallback if CPU-bound.

3
STT

Gateway feeds frames to streaming STT (managed API for v1; self-hosted whisper later). Partial transcripts can stream back to the listening template for live feedback.

4
router

On PTT-up, final transcript → intent classify → command published to the focused agent. Loop rejoins §04 ▼ step 3.

12Security model

Voice → remote code execution, by design

The core threat

An agent with a Bash tool will run whatever prompt it's handed. Anyone who can push a cmd down an agent's connection effectively has a shell on that machine. So the multi-tenant identity and isolation of §03 are not optional hardening — they are the foundation the rest of the system stands on. There is no "insecure mode" to start from; the first connection a principal makes is already tenant-scoped and authenticated.

Identity & transport

mTLS or per-principal tokens presented at the WS upgrade for every adapter and device. WSS everywhere. Each principal is bound to exactly one tenantId and one id.

Tenant scoping

The authenticated principal fixes the tenant; the Commander stamps it on every inbound message and refuses any id outside that tenant. Authz lives in one place — the app layer that already routes — not split across broker config.

Command authorization

The Commander checks device→agent ownership within the tenant before routing any prompt. Optional per-agent confirmation step for high-blast-radius modes (e.g. bypass-permissions).

Device pairing

Onboarding mints a per-device cert (captive-portal/BLE enroll → short-lived claim code → cert). Lost device → revoke its cert; it can no longer command anything.

Security review is continuous, not a phase: every change to routing, auth, or the command path is reviewed against the cross-tenant and RCE threat models before it ships.
